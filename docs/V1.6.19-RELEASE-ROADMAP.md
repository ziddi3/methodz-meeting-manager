# Methodz Meeting Manager v1.6.19 Release Roadmap

## Release intent

Add a static Workspace Home that makes the existing application lifecycle easier to enter and deploy without changing the meeting-record schema, activating a hosted provider, or hiding record reads behind page startup.

## Definition of done

- [x] `index.html` is a real static root entry point.
- [x] Preparation, Meeting-Day, Decision Register, Meeting Outcomes, Archive, and Verify workflows are reachable from the root.
- [x] A portable aggregate snapshot core returns counts only.
- [x] Browser-local records are read only after explicit operator refresh.
- [x] Active, completed, archived, upcoming, unscheduled, overdue, unassigned, and needs-scheduling signals are represented.
- [x] Record and task processing are bounded and truncation is visible.
- [x] Meeting identity and protected meeting text are absent from the snapshot report.
- [x] The PWA identity remains stable while the installed launch route moves to Workspace Home.
- [x] Service-worker changes cache static assets only.
- [x] Portable, Chromium, mobile, privacy, malformed-storage, architecture, and deployment-boundary coverage is included.
- [x] Application shell remains `1.6.12`.
- [x] Meeting-record schema remains `1.6.0`.
- [x] Browser-local storage remains the default provider.
- [x] No automatic record mutation, assignment, reminder, notification, archive, transfer, provider call, or synchronization is introduced.
- [x] No deployment identity for `hub.methodz.ca` is introduced.

## Preserved 1.x boundary

This release is lifecycle and deployment hardening, not a 2.0 provider transition. A production provider still requires explicit approval and evidence for authentication, authorization, tenant isolation, encryption, audit, retention, recovery, residency, and incident response.

## Next evidence targets

After Workspace Home is merged, the 1.x roadmap should continue with real-device evidence and operator ergonomics rather than expanding hidden automation:

1. run Android, iOS, tablet, and two-device field rehearsals from the root launch surface;
2. capture large-workspace timing evidence using existing bounded diagnostics;
3. evaluate whether Calendar or CRM integration belongs in the explicitly approved 2.0 provider phase;
4. preserve counts-only and read-only derived workspaces unless a later roadmap item explicitly grants write authority.
