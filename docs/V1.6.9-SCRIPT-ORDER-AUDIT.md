# Methodz Meeting Manager v1.6.9 Script-Order Audit

## Why script order matters

The application intentionally remains a static collection of plain browser scripts. Later layers extend functions and configuration created by earlier layers, so script order is part of the runtime contract.

Version 1.6.9 audits that contract without performing a risky module rewrite.

## Current dependency sequence

### Configuration

```text
config.js
config-v11.js ... config-v168.js
config-v169.js
```

Each versioned file extends `window.METHODZ_MEETING_CONFIG`. The newest configuration must load last so `appShellVersion` resolves to `1.6.9` while `schemaVersion` remains `1.6.0`.

### Migrations

```text
migrations.js
migrations-v10.js ... migrations-v16.js
```

No v1.6.9 record migration exists because this release does not change meeting-record fields or the record schema.

### Provider, synchronization, and package cores

```text
provider-contract.js
hosted-provider-adapters.js
http-provider-pilot.js
sync-rehearsal-core.js
sync-rehearsal-hardening.js
sync-queue-portability.js
data-adapter.js
async-data-adapter.js
attachment-adapter.js
crypto-package-core.js
key-custody-core.js
workspace-package-core.js
cross-device-transfer-core.js
transfer-acceptance-core.js
```

`transfer-acceptance-core.js` is intentionally placed after the workspace and transfer cores. It is DOM-independent and does not alter those earlier APIs.

### Core workspace and feature layers

```text
app.js
features-v03*.js ... features-v167*.js
features-v168-transfer-rehearsal.js
features-v169-transfer-acceptance.js
features-v169-meeting-day.js
```

The acceptance layer loads after v1.6.8 because it reads the completed transfer state and pre-import recovery package.

Meeting-day mode loads last because it classifies the cards installed by every previous feature layer. Loading it earlier would leave later infrastructure panels outside its collapse controls.

## Safe consolidation candidates

The following areas are candidates for future consolidation behind stable facade APIs:

1. **Configuration overlays**
   - Generate a single production configuration during a future optional build process.
   - Keep the checked-in overlay files for direct-file compatibility and historical clarity until parity is proven.

2. **Workspace package operations**
   - Consolidate package creation, inspection, restore planning, transaction application, and read-back verification into one facade.
   - Preserve existing global function names as compatibility aliases.

3. **Transfer operations**
   - Group v1.6.8 transfer and v1.6.9 acceptance workflows behind a `MethodzTransferWorkspace` namespace.
   - Keep source export, destination import, acceptance, and rollback as separate explicit operator stages.

4. **UI panel installation**
   - Introduce a registry that assigns panel IDs, labels, groups, and preferred insertion anchors.
   - Meeting-day mode could then use registry metadata rather than heading matching.

5. **Metadata report utilities**
   - Share bounded history persistence, download handling, escaping, byte formatting, and status announcements.

6. **Test server and Playwright setup**
   - Reuse one composite CI action or script for Node setup, Playwright installation, static server startup, and trace upload.

## Unsafe consolidation candidates

Do not combine these without a separate migration and regression plan:

- record migrations with application-shell configuration;
- active records and Archive Vault storage;
- private signing-key handling with public-key custody records;
- service-worker cache logic with synchronization or transfer queues;
- transfer import with acceptance or rollback into one automatic transaction;
- meeting-day preferences with meeting-record content;
- external export redaction with source-record mutation.

## Recommended next architecture step

Create a non-breaking panel registry first. It can be added as an optional facade while existing direct DOM insertion remains operational. Once every layer registers its panel metadata and CI proves identical ordering, meeting-day mode and navigation can stop relying on heading text.

A later consolidation should proceed one boundary at a time:

1. add facade;
2. keep compatibility aliases;
3. move one consumer;
4. run complete browser matrix;
5. remove duplicated internals only after at least one stable release.

## Verified v1.6.9 order

The v1.6.9 workflow checks that:

- configuration loads after v1.6.8;
- the metadata core loads before its UI;
- acceptance loads after transfer;
- meeting-day mode loads last;
- the archive page receives only the configuration overlay;
- the service worker caches all new static assets;
- no new core or UI script is loaded in `verify.html` or the archive runtime unnecessarily.
