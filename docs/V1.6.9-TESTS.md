# Methodz Meeting Manager v1.6.9 Test Plan

## Release gate

Version 1.6.9 is ready to merge only when:

- every JavaScript and module file passes `node --check`;
- the metadata-only core suite passes;
- the two-profile browser transfer, acceptance, diagnostics, and rollback rehearsal passes;
- meeting-day mode works at a narrow phone viewport without horizontal overflow;
- all existing static, browser, recovery, custody, cryptographic, provider, synchronization, mobile, and transfer workflows remain green;
- the application shell remains static and the meeting-record schema remains `1.6.0`.

## Automated core checks

Run:

```bash
node tests/v169-transfer-acceptance.mjs
```

The suite verifies:

- classification of active records, archived records, revisions, directories, templates, governance metadata, public keys, custody records, recovery logs, and tenant queues;
- aggregate item, entry, and byte counts;
- deterministic component fingerprints;
- acceptance blocking when transfer verification is absent;
- acceptance blocking when any checklist component remains unchecked;
- successful acceptance only after all required checks;
- quota and soft-storage warning generation;
- rollback report flags and counts;
- exclusion of meeting values, raw identifiers, attendee data, key identifiers, and queue identifiers from generated reports.

## Automated browser checks

Run after starting a static server on port 4173:

```bash
npx playwright test tests/v169-transfer-acceptance.spec.js --reporter=line
```

The browser suite uses two isolated browser contexts to represent source and destination profiles.

### Meeting-day mode

The test verifies:

- the meeting-day control is available;
- entering meeting-day mode preserves the direct capture sections;
- supporting panels are collapsed rather than deleted;
- **Show Tools** restores supporting panels;
- section navigation records and restores the last section;
- the state survives a page reload;
- the 390-pixel viewport has no page-level horizontal overflow.

### Transfer acceptance

The test verifies:

- a disposable source profile creates a complete workspace package;
- the destination profile begins with separate local data;
- the v1.6.8 transfer package verifies;
- the no-write recovery drill passes;
- explicit transfer confirmations and typed approval are required;
- the destination receives the source workspace and independently bound queue data;
- the v1.6.9 acceptance checklist contains all ten required components;
- acceptance evidence is stored only after all components are reviewed;
- acceptance reports exclude disposable meeting content and raw record identifiers.

### Diagnostics

The test verifies:

- aggregate diagnostics complete after transfer;
- the report is persisted;
- the report excludes meeting content and storage-key names.

### Rollback rehearsal

The test verifies:

- the pre-import recovery package verifies;
- the rollback plan is previewed without writes;
- typed `ROLLBACK` approval and final confirmation are required;
- the current destination is preserved as a separate rollback-recovery package;
- the pre-import destination snapshot is restored;
- read-back verification succeeds;
- rollback reports remain metadata-only.

## Manual phone and tablet checks

Use a real phone or tablet where available.

1. Open `meeting.html` over HTTPS or localhost.
2. Enter Meeting-Day Mode.
3. Move through Info, Organizations, Attendance, Agenda, Notes, Decisions, Tasks, Summary, and Save.
4. Confirm the sticky section bar remains usable in portrait and landscape.
5. Add an attendee and a task.
6. Enter long notes and confirm no horizontal overflow.
7. Open and close supporting tools.
8. Reload and confirm the last section and meeting-day preference return.
9. Exit Meeting-Day Mode and confirm every earlier panel is visible.

## Manual transfer acceptance checks

1. Complete a v1.6.8 source export and destination import using disposable data.
2. Reload the destination.
3. Confirm the acceptance panel detects `destination-import-verified`.
4. Compare every aggregate component count with the source.
5. Leave one item unchecked and confirm acceptance is blocked.
6. Review all items and complete acceptance.
7. Download and inspect the report.
8. Confirm no meeting text, names, signatures, raw IDs, credentials, or private-key values appear.
9. Run diagnostics and inspect its report for the same exclusions.

## Manual rollback checks

1. Confirm the destination contains the transferred disposable records.
2. Press **Preview Rollback**.
3. Confirm no records change during preview.
4. Alter the destination after preview and confirm the rollback is invalidated.
5. Preview again.
6. Confirm the review checkbox and typed phrase are both required.
7. Apply the rollback.
8. Confirm the original destination records return.
9. Confirm `methodzTransferRollbackRecoveryV169` contains a recovery package for the replaced transferred workspace.
10. Download and inspect the rollback report.

## Direct-file compatibility

Open `meeting.html` directly with a `file:` URL.

Expected behavior:

- core meeting preparation, capture, saving, archive, and export remain available;
- meeting-day mode remains available;
- browser features that require HTTPS or localhost may report unavailable;
- no module requires a build command or remote runtime package.

## Failure expectations

The following must fail closed without changing workspace data:

- missing or malformed pre-import recovery package;
- checksum mismatch;
- missing verified transfer state;
- incomplete acceptance checklist;
- changed destination after rollback preview;
- missing typed rollback phrase;
- read-back mismatch after restoration.
