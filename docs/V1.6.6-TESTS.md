# Methodz Meeting Manager v1.6.6 Test Plan

## Automated gate

The `Mobile Readiness` GitHub Actions workflow performs:

1. JavaScript syntax validation for the v1.6.6 configuration, feature, and test files.
2. Entry-point, archive, service-worker, manifest, and version wiring checks.
3. A static server boot check.
4. Playwright Chromium tests at a `390 × 844` phone viewport.

## Browser assertions

`tests/v166-mobile-readiness.spec.js` verifies:

- no page-level horizontal overflow at the phone viewport;
- the four-button mobile action dock is visible;
- mobile dock controls meet the 44-pixel touch-target minimum;
- the meeting-title input uses at least a 16-pixel font size;
- Device Readiness produces app-shell `1.6.6` and schema `1.6.0` metadata;
- readiness output excludes marker text placed in meeting title and discussion notes;
- report boundaries explicitly exclude meeting content, record IDs, credentials, and private key material;
- Records and Device dock actions reach the intended sections;
- the refresh action completes and renders seven capability checks.

## Manual phone test

Test on at least one Android Chromium browser and one iOS Safari browser:

1. Open `meeting.html` from the intended host.
2. Confirm the header, quick actions, meeting information, attendance, agenda, notes, tasks, summary, and saved records fit without page-level horizontal scrolling.
3. Tap each mobile dock action.
4. Enter text into every field and confirm the browser does not zoom unexpectedly.
5. Add and remove an attendee, task, decision, and attachment reference.
6. Save a meeting and reopen it from Saved Meeting Records.
7. Switch offline and confirm the hosted app shell remains available when a service worker controls the page.
8. Refresh Device Readiness before and after switching network state.
9. Download a readiness report and confirm it contains counts and capabilities only.
10. Print or save PDF and confirm the readiness panel and mobile dock are absent.

## Cross-device rehearsal

Use disposable or test records only:

1. Export a complete Workspace Backup on the source device.
2. Run a recovery inspection and dry drill on the destination device.
3. Confirm the proposed mutation plan.
4. Restore in a separate browser profile.
5. Compare active, archived, revision, template, directory, governance, receipt, and key-registry counts.
6. Open representative records and independently verify public-key IDs.
7. Preserve the source browser until destination verification is complete.

## Failure interpretation

- **Storage unavailable** is a release blocker for that browser context.
- **Horizontal overflow** requires identifying the exact feature panel responsible before release.
- **Persistent storage not granted** is a warning, not a blocker.
- **Service worker inactive in direct-file mode** is expected.
- **Web Crypto unavailable** limits signing and verification but does not block core meeting capture.
- A passed readiness report is not proof of backup, restore, authorization, or legal compliance.
