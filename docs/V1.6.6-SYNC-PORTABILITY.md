# Methodz Meeting Manager v1.6.6 Synchronization Queue Portability

## Release purpose

Version 1.6.6 hardens the browser-local synchronization rehearsal introduced in v1.6.5. It makes rehearsal queues portable, reviewable, integrity-checked, and recoverable without connecting production infrastructure or weakening the offline-first meeting workflow.

The meeting-record schema remains `1.6.0`. The application shell advances to `1.6.6`.

## Canonical product boundary

Methodz Meeting Manager remains a task-focused meeting preparation, capture, analysis, archive, and records tool. Queue portability supports the durability of that work. It does not convert the application into Method Hub, Nexus Hub, a Cathedral component, a business storefront, or a general infrastructure platform.

The release does not deploy to or replace `hub.methodz.ca`.

## Queue package contract

A queue export uses:

```text
packageType: methodz-sync-rehearsal-queue
packageVersion: 1.0.0
integrity.algorithm: fnv1a32-canonical-json
```

The package contains the complete tenant-scoped rehearsal queue so pending or uncertain work can be moved between browser profiles. Because a queue entry may contain the record snapshot required to complete an explicit push or pull, a queue package must be handled with the same care as a meeting workspace backup.

Every import is validated before mutation:

1. the top-level object and package type are checked;
2. the package version must be supported;
3. the export timestamp must be valid;
4. the tenant identifier and opaque tenant reference must agree;
5. the expected active tenant must match;
6. every entry must have a supported operation, state, version, identifier, record identifier, idempotency key, and timestamps;
7. duplicate queue identifiers are rejected;
8. private keys, private JWK parameters, credentials, embedded binary fields, and data URLs are rejected;
9. the canonical integrity value must verify;
10. entry limits must be respected.

A rejected package never changes local queue data.

## Explicit import preview and approval

Selecting a package produces a no-write preview showing:

- opaque tenant reference;
- package generation time;
- total queue entries;
- push and pull counts;
- conflict count;
- protected-work count;
- warnings from declared-summary comparison.

The user must then choose a merge strategy and explicitly approve the import. Importing does not process any queue entry. Remote or local record mutation still requires a separate Process action.

## Merge strategies

### Keep local

When queue IDs collide, the browser-local entry is retained. Imported entries with new IDs are added.

### Prefer newest metadata

When queue IDs collide, the entry with the later `updatedAt` timestamp is retained. This strategy does not silently process either entry.

### Retain both

The local entry is retained and the imported collision receives a deterministic regenerated queue identifier. The original imported identifier is preserved as `importedFromId` for troubleshooting.

Merges fail closed if the resulting queue exceeds the configured limit.

## Completed-entry compaction

Compaction is a review workflow, not automatic cleanup.

The application may propose old completed entries for removal. It never proposes or permits removal of:

- pending work;
- offline work;
- retryable failures;
- blocked conflicts.

The operator selects completed candidates and confirms removal. Meeting records and the disposable remote are not deleted by queue compaction.

## Operator evidence

The application keeps a bounded, tenant-scoped browser-local event log for:

- enqueue;
- process;
- retry;
- discard;
- connectivity changes;
- pull preview;
- conflict decision;
- queue import;
- queue export;
- compaction review;
- compaction application.

Exported operator evidence contains only approved metadata:

- opaque tenant and queue references;
- operation and queue state;
- bounded result and error codes;
- selected strategy;
- numeric counts;
- timestamps.

It excludes meeting content, record IDs, tenant IDs, idempotency keys, raw conflict tokens, signatures, credentials, access tokens, private keys, and binary content.

Browser-local evidence does **not** prove delivery, identity, authorization, remote acceptance, or legal approval. A future production provider must supply authenticated server-side audit evidence independently.

## Workspace backup and recovery

Tenant queue and operator-event keys begin with `methodz`, so the existing workspace backup and recovery system recognizes them automatically. Version 1.6.6 tests verify that a tenant-scoped queue key:

- is recognized by `workspace-package-core.js`;
- participates in checksum inspection;
- appears in a controlled restore plan;
- remains subject to private-key exclusion and package-size limits.

## Service-worker boundary

The service worker caches static application assets only.

It deliberately has:

- no `sync` event handler;
- no background queue processor;
- no access to meeting-record or rehearsal-queue values;
- no automatic push, pull, retry, import, merge, compaction, or conflict decision.

All synchronization rehearsal actions require an open page and an explicit user action.

## Deployment

The release remains deployable as plain static files:

- no framework;
- no build command;
- no required runtime package;
- no production endpoint;
- no credentials;
- no server requirement;
- direct-file meeting workflows remain available;
- normal static hosting and the optional PWA shell remain supported.
