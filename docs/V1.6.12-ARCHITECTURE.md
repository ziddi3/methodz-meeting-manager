# v1.6.12 Workspace Capacity Architecture

## Product role

Methodz Meeting Manager remains a task-focused meeting preparation, capture, analysis, follow-up, archive, recovery, transfer, and records tool. The capacity workspace supports that direct product purpose. It is not Method Hub, Nexus Hub, a storefront, the Cathedral, or a hosted provider.

## Release boundary

- App shell: `1.6.12`
- Meeting-record schema: `1.6.0`
- Workspace capacity core: `1.0.0`
- Runtime: semantic HTML, CSS, and vanilla JavaScript
- Deployment: direct-file use and ordinary static hosting
- Default provider: browser-local storage

No backend, production endpoint, credential, framework, runtime package, build step, schema migration, automatic cleanup, or background synchronization is introduced.

## Modules

### `workspace-capacity-core.js`

A portable core with side-effect-free report builders and a read-only storage collector that:

- estimates UTF-8 bytes for an in-memory storage snapshot while reusing one `TextEncoder` instance for all measurements;
- enumerates every browser-local key name and sorts the names before deterministic selection;
- reads values and retains raw snapshot entries for no more than the configured maximum while preserving the complete `totalEntries` count and accurate truncation state;
- returns an explicit unavailable report when storage length access, key enumeration, selected-value collection, or the final length consistency check fails;
- groups entries into stable aggregate categories without returning raw key names or values;
- evaluates archive classification before active-record classification so archive storage is counted only as **Archive Vault**;
- combines measured localStorage use with an optional browser origin estimate;
- applies bounded warning and critical thresholds;
- generates bounded recommendations that never instruct automatic deletion;
- creates a synthetic Follow-Up Review workload entirely in memory;
- returns metadata-only performance results;
- builds a metadata-only downloadable report.

### `features-v1612-workspace-capacity.js`

The browser layer creates the Workspace Capacity panel after the Follow-Up Review. It performs no scan at startup. Operators must explicitly run a capacity check or synthetic performance rehearsal.

An available capacity check renders the bounded scanned-entry count and aggregate categories. A failed storage collection renders `unavailable`, not `healthy`, and does not render “No browser-local entries were measured.” Its report has `availability.localStorage` set to `unavailable`, the fixed `local-storage-read-failed` code, null local scan counts and measured bytes, and no categories. The interface uses generic recovery text rather than a raw exception.

The Workspace Capacity and Cross-Device Transfer panels are marked as non-meeting control surfaces. Their inputs do not schedule the app shell's meeting-draft autosave, preventing a diagnostics action from writing a draft and preventing transfer approvals from invalidating their own no-write drill fingerprint. Meeting capture controls retain their existing autosave behavior.

The browser layer may call `navigator.storage.estimate()` when available. That estimate can include static caches or other origin storage, so the interface distinguishes it from measured localStorage bytes.

### `features-v1612.css`

Responsive metrics, category, and control layouts preserve narrow-phone usability without changing historical styles.

## Privacy and mutation boundaries

Capacity reports contain category labels, aggregate entry counts, aggregate byte counts, thresholds, duration, and bounded recommendations. They exclude:

- raw storage keys and values;
- meeting text and record identifiers;
- attendee names, consent, and typed signatures;
- credentials, private keys, provider secrets, and signature material;
- queue payloads and hidden governance metadata.

All key names are enumerated to validate the complete entry set and produce a stable bounded selection; selected values exist only in the in-memory snapshot used for measurement. Neither is copied into the report or rendered interface. Unavailable reports contain only the generic availability state and fixed error code; raw browser `Error` objects, names, messages, and stacks are excluded.

The synthetic rehearsal uses temporary JavaScript objects only. It does not save records, append revisions, update task status, enqueue synchronization, write evidence, or alter browser-local storage.

## Script order

1. `config-v1612.js` loads after `config-v1611.js`.
2. `meeting-review-core.js` loads before `workspace-capacity-core.js` consumers.
3. `workspace-capacity-core.js` loads before `app.js` and browser features.
4. `features-v1611-follow-up-review.js` creates the Follow-Up Review.
5. `features-v1612-workspace-capacity.js` creates the capacity panel.
6. `features-v1610-panel-registry.js` binds the completed dynamic shell.
7. Meeting-Day navigation consumes registry metadata last.

## Service worker

The service worker caches the new static assets only. It never reads localStorage, runs capacity scans, performs synthetic rehearsals, cleans data, mutates records, processes queues, or synchronizes in the background.
