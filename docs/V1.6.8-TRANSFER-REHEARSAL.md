# Methodz Meeting Manager v1.6.8 Cross-Device Transfer Rehearsal

## Purpose

Version 1.6.8 turns the existing workspace backup, synchronization queue portability, operator evidence, recovery inspection, and Device Readiness layers into one explicit cross-device rehearsal.

The feature is designed for a controlled move between browser profiles or devices without connecting production infrastructure or weakening the offline-first model.

## What the transfer bundle contains

The bundle contains four independently validated components:

1. Complete Methodz Meeting Manager workspace package.
2. Tenant-scoped synchronization rehearsal queue package.
3. Metadata-only synchronization operator-evidence package.
4. Metadata-only Device Readiness report.

The bundle itself has a separate integrity checksum and manifest.

Because it contains workspace values and meeting records, treat it like a complete business backup. Keep it outside public folders, source repositories, and ordinary chat messages.

## What is excluded

The transfer process fails closed when it detects:

- private signing keys;
- private JWK parameters;
- provider credentials, passwords, tokens, API keys, or secrets;
- production endpoint configuration;
- embedded binary payloads rejected by the provider boundary.

Metadata-only rehearsal reports exclude meeting content, raw record IDs, attendee names, signatures, raw queue IDs, credentials, and private-key material.

## Source procedure

1. Save current meeting work.
2. Confirm private signing keys are stored separately.
3. Run Device Readiness.
4. Select **Build & Download Transfer Bundle**.
5. Store the downloaded file outside the source browser and device.
6. Keep the source workspace unchanged until destination verification is complete.

## Destination procedure

1. Open the app in the destination browser profile.
2. Run Device Readiness.
3. Choose the transfer bundle.
4. Confirm transfer, workspace, queue, operator-evidence, and readiness validation.
5. Review duplicate and collision counts across active records, Archive Vault entries, revision groups, public verification keys, and synchronization queue entries.
6. Run the no-write recovery drill.
7. Review the add, replace, unchanged, remove, and ignored mutation counts.
8. Complete every destination confirmation.
9. Type `TRANSFER`.
10. Approve the final confirmation dialog.
11. Reload the destination workspace after post-import verification.
12. Download and retain the pre-import recovery package until the transfer is accepted.
13. Export a fresh destination workspace backup.

## Mutation and rollback behavior

The destination import:

- revalidates the transfer immediately before mutation;
- creates a complete pre-import recovery package first;
- replaces recognized Methodz workspace entries only after explicit approval;
- verifies every imported storage value against the inspected package;
- restores the original destination snapshot if a write or verification step fails;
- preserves v1.6.8 local control-state and report entries;
- never processes synchronization queue work automatically.

## Collision review

Collision reports use opaque hashed references rather than raw identifiers. The following categories are reviewed:

- incoming active record versus local active record;
- incoming archived record versus local archived record;
- incoming active record versus local archive;
- incoming archive versus local active record;
- revision group;
- public verification key;
- synchronization queue entry.

A collision is not automatically resolved. The destination operator must review it before approving replacement.

## Evidence boundaries

A rehearsal report records package-integrity results, aggregate counts, collision counts, checkpoints, recovery creation, mutation outcome, rollback outcome, and post-import verification.

It does not prove:

- a person's identity;
- device identity;
- authority to release or receive records;
- remote delivery;
- legal approval;
- production-provider durability.

## Deployment boundary

Version 1.6.8 remains plain HTML, CSS, and JavaScript. There is no framework, build command, runtime package, mandatory server, production endpoint, credential, silent merge, background transfer, or automatic synchronization.

The service worker caches static assets only. It does not read, transmit, import, or process transfer packages or synchronization queues.
