# Methodz Meeting Manager v1.6.9 Architecture

## Release boundary

- Application shell: `1.6.9`
- Meeting-record schema: `1.6.0`
- Default provider: browser `localStorage`
- Runtime dependencies: none
- Build command: none
- Production endpoint: none
- Automatic synchronization: none

Version 1.6.9 is an application-shell and operator-workflow release. It does not introduce an ordered record migration because meeting records are unchanged.

## New files

```text
config-v169.js
transfer-acceptance-core.js
features-v169-transfer-acceptance.js
features-v169-meeting-day.js
features-v169.css
```

## Configuration layer

`config-v169.js` extends the existing configuration after `config-v168.js`.

It adds bounded browser-local keys for:

- transfer acceptance state;
- acceptance and rollback reports;
- the rollback-recovery package;
- meeting-day preferences;
- workspace diagnostics reports.

It explicitly disables automatic acceptance, rollback, synchronization, production endpoints, production credentials, private-key storage, and service-worker workspace access.

## Metadata core

`transfer-acceptance-core.js` is a DOM-independent CommonJS/browser-compatible core. It provides:

- deterministic component classification;
- aggregate count and byte summaries;
- metadata-only acceptance reports;
- metadata-only diagnostics reports;
- metadata-only rollback reports;
- stable serialization and FNV-1a checksums.

The core receives storage values only long enough to calculate aggregate metadata. Returned reports do not include values, key names, or raw business identifiers.

## Transfer acceptance UI

`features-v169-transfer-acceptance.js` depends on:

1. the merged configuration through `config-v169.js`;
2. `workspace-package-core.js`;
3. `transfer-acceptance-core.js`;
4. the v0.8 workspace package creator;
5. the v1.6.8 transfer state and pre-import recovery package.

The layer is deliberately loaded after `features-v168-transfer-rehearsal.js`. It does not wrap or replace v1.6.8 functions.

### Acceptance state

Acceptance is represented separately from meeting records and the v1.6.8 transfer report. A completed acceptance stores:

- stage;
- timestamp;
- report checksum;
- aggregate component fingerprint;
- application-shell version;
- record-schema version.

Changing the aggregate workspace snapshot invalidates the visual “already accepted” state until the operator refreshes and reviews it again.

### Rollback transaction

The rollback path follows this order:

1. parse and checksum-verify the pre-import package;
2. create a no-write restore plan;
3. fingerprint the current destination;
4. require review, typed phrase, and final confirmation;
5. create a current-destination recovery package;
6. replace recognized workspace entries;
7. read back the exact expected key set and values;
8. restore and verify the original destination if the mutation fails;
9. persist a bounded metadata-only report.

The v1.6.9 control keys and the original v1.6.8 transfer state are preserved across the rehearsal so evidence remains available.

## Meeting-day UI

`features-v169-meeting-day.js` is loaded last so it can classify panels installed by every earlier feature layer.

It identifies the core capture path by existing heading text and assigns stable section IDs at runtime:

```text
Meeting Information
Organizations / Representatives Present
Attendance Sign-On
Agenda Checklist
Discussion Notes
Decisions Made
Follow-Up Tasks
Meeting Summary
End of Meeting
```

All other direct-child cards are marked as supporting tools. In meeting-day mode they are hidden through the standard `hidden` attribute until the operator presses **Show Tools**. No panel is deleted, and leaving meeting-day mode restores the complete workspace.

Preferences store only mode state, tool expansion state, last section ID, timestamp, and application-shell version.

## Static app shell

`service-worker.js` advances its static cache namespace to `methodz-meeting-manager-v1.6.9` and caches the new configuration, core, UI, and stylesheet files.

The worker has no background-sync, transfer-import, acceptance, rollback, diagnostics, workspace, or queue-processing handler.

## Failure behavior

- Missing transfer state blocks acceptance.
- Incomplete checklist review blocks acceptance.
- Missing or invalid pre-import packages block rollback.
- Workspace changes after preview invalidate rollback approval.
- Failed read-back triggers restoration of the original destination snapshot.
- Failed diagnostics do not change workspace state.
- All report histories are bounded.
