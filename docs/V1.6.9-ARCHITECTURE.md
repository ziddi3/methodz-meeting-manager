# Methodz Meeting Manager v1.6.9 Architecture

## Release boundary

- Application shell: `1.6.9`
- Meeting-record schema: `1.6.0`
- Default provider: browser `localStorage`
- Runtime dependencies: none
- Build command: none
- Production endpoint: none
- Automatic synchronization: none

Version 1.6.9 is an application-shell and operator-workflow release. It does not introduce an ordered record migration because meeting records are unchanged.

## New files

```text
config-v169.js
transfer-acceptance-core.js
transfer-acceptance-summary-filter.js
features-v169-transfer-acceptance.js
```

## Configuration layer

`config-v169.js` extends the existing configuration after `config-v168.js`.

It adds bounded browser-local keys for:

- transfer acceptance state;
- acceptance and rollback reports;
- the rollback-recovery package;
- meeting-day preferences;
- workspace diagnostics reports.

It explicitly disables automatic acceptance, rollback, synchronization, production endpoints, production credentials, private-key storage, and service-worker workspace access.

## Metadata core

`transfer-acceptance-core.js` is a DOM-independent CommonJS/browser-compatible core. It provides:

- deterministic component classification;
- aggregate count and byte summaries;
- metadata-only acceptance reports;
- metadata-only diagnostics reports;
- metadata-only rollback reports;
- stable serialization and FNV-1a checksums.

The core receives storage values only long enough to calculate aggregate metadata. Returned reports do not include values, key names, or raw business identifiers.

`transfer-acceptance-summary-filter.js` wraps only the browser-facing component-summary function. It removes operational evidence and UI-control entries before calculating an acceptance fingerprint or diagnostic component summary. Excluded entries include:

- the active meeting draft;
- pre-restore and rollback-recovery packages;
- transfer state and transfer reports;
- device-readiness reports;
- acceptance state and acceptance reports;
- diagnostics reports;
- accessibility and meeting-day preferences.

This prevents acceptance or diagnostics evidence from changing the reviewed snapshot immediately after it is written. Records, Archive Vault records, revisions, directories, templates, governance metadata, public keys, custody records, recovery logs, and synchronization queue state remain included.

## Transfer acceptance UI

`features-v169-transfer-acceptance.js` depends on:

1. the merged configuration through `config-v169.js`;
2. `workspace-package-core.js`;
3. `transfer-acceptance-core.js` plus the browser evidence filter;
4. the v0.8 workspace package creator;
5. the v1.6.8 transfer state and pre-import recovery package.

The layer is deliberately loaded after `features-v168-transfer-rehearsal.js`. It does not wrap or replace v1.6.8 functions.

### Acceptance state

Acceptance is represented separately from meeting records and the v1.6.8 transfer report. A completed acceptance stores:

- stage;
- timestamp;
- report checksum;
- aggregate component fingerprint;
- application-shell version;
- record-schema version.

Changing the substantive aggregate workspace snapshot invalidates the visual “already accepted” state until the operator refreshes and reviews it again. Writing acceptance or diagnostics evidence does not invalidate that state.

### Rollback transaction

The rollback path follows this order:

1. parse and checksum-verify the pre-import package;
2. create a no-write restore plan;
3. fingerprint the current destination;
4. require review, typed phrase, and final confirmation;
5. create a current-destination recovery package;
6. replace recognized workspace entries;
7. read back the exact expected key set and values;
8. restore and verify the original destination if the mutation fails;
9. persist a bounded metadata-only report;
10. transition the prior destination-transfer state to `rolled-back-to-pre-import`.

The v1.6.9 control keys remain available across the rehearsal so recovery evidence can be inspected. The v1.6.8 transfer state is retained only as a non-verified rollback marker, which prevents the restored pre-import workspace from being accepted under stale transfer verification.

`features-v169-rollback-stability.js` separates substantive workspace changes from the ordinary meeting-draft write caused by checking the rollback review box or typing the approval phrase. It records a fingerprint that excludes only known volatile control keys. Immediately before apply, it refreshes the internal full preview only when every non-volatile workspace entry still matches the reviewed snapshot. Any record, archive, revision, directory, template, governance, custody, recovery, queue, or other substantive change continues through the original fail-closed invalidation path.

This hardening prevents control-entry autosave from invalidating its own rollback approval without weakening the rule that real workspace changes require a new preview.

## Meeting-day UI

`features-v169-meeting-day.js` is loaded last so it can classify panels installed by every earlier feature layer.

It identifies the core capture path by existing heading text and assigns stable section IDs at runtime:

```text
Meeting Information
Organizations / Representatives Present
Attendance Sign-On
Agenda Checklist
Discussion Notes
Decisions Made
Follow-Up Tasks
Meeting Summary
End of Meeting
```

All other direct-child cards are marked as supporting tools. When configured to collapse, Meeting-Day Mode records each card's existing `hidden` state, hides only the supporting cards it controls, and restores the previous state when tools are shown or the mode is exited. A panel that was already hidden, such as an unopened minutes preview, remains hidden.

`meetingDay.collapseSecondaryTools` is authoritative. Setting it to `false` keeps supporting tools visible while retaining section navigation and the compact meeting-day shell.

Preferences store only mode state, tool expansion state, last section ID, timestamp, and application-shell version.

## Static app shell

`service-worker.js` advances its static cache namespace to `methodz-meeting-manager-v1.6.9` and caches the new configuration, metadata core, evidence filter, UI, hardening, and stylesheet files.

The worker has no background-sync, transfer-import, acceptance, rollback, diagnostics, workspace, or queue-processing handler.

## Failure behavior

- Missing transfer state blocks acceptance.
- Incomplete checklist review blocks acceptance.
- Operational evidence cannot self-inflate an acceptance snapshot.
- Missing or invalid pre-import packages block rollback.
- Substantive workspace changes after preview invalidate rollback approval.
- Draft-only approval-control autosave is revalidated without bypassing substantive-change detection.
- Successful rollback invalidates the previous verified transfer state.
- Failed read-back triggers restoration of the original destination snapshot.
- Failed diagnostics do not change workspace state.
- All report histories are bounded.
