# Methodz Meeting Manager v1.6.9 Architecture

## Classification

Methodz Meeting Manager is a task-focused meeting preparation, capture, analysis, archive, and records tool. Infrastructure in this release supports that direct purpose. It does not turn the application into Method Hub, Nexus Hub, a storefront, the Cathedral, or shared Methodz infrastructure.

## New layers

### `config-v169.js`

Advances the app shell to `1.6.9` while preserving record schema `1.6.0`. It defines bounded browser-local keys and settings for acceptance reports, rollback evidence, pre-rollback recovery, Meeting-Day preferences, and aggregate diagnostics.

### `transfer-acceptance-core.js`

A dependency-free browser and Node core layered on `workspace-package-core.js`.

Responsibilities:

- build a verified package from current recognized workspace entries;
- classify destination data into acceptance categories;
- compare active, archived, revision, and queue counts with the latest verified transfer report;
- verify the pre-import recovery package;
- build metadata-only acceptance evidence;
- build a no-write rollback plan;
- build metadata-only rollback evidence;
- measure aggregate workspace size and parse health;
- expose an explicit metadata-boundary assertion.

The core never reads `localStorage` directly and never performs mutations.

### `features-v169-transfer-acceptance.js`

Browser orchestration and UI.

Responsibilities:

- collect recognized browser-local workspace entries;
- locate the latest verified v1.6.8 destination-import report;
- run and render acceptance checks;
- collect explicit operator confirmations;
- preview and apply rollback only after checksum validation, typed approval, and final confirmation;
- save the current transferred state before rollback;
- verify writes and removals;
- restore the transferred snapshot if rollback fails;
- persist bounded metadata-only reports;
- run and export aggregate diagnostics.

### `features-v169-meeting-day.js`

Progressively classifies existing cards at runtime. It does not duplicate the meeting form or introduce a second data model.

Responsibilities:

- identify the nine direct meeting sections by their existing headings;
- add stable section IDs and an accessible navigation strip;
- hide supporting panels only while Meeting-Day Mode is active;
- preserve an explicit control for expanding those panels;
- restore mode and last-section preferences;
- provide `Alt+M` as an optional keyboard shortcut.

### `features-v169.css`

Adds responsive acceptance, rollback, diagnostics, and Meeting-Day presentation. Supporting panels are hidden only through a body class and reappear when the mode exits or the operator expands them. Print output does not include the v1.6.9 infrastructure panels.

## Script order

The required order is:

1. all configuration layers through `config-v169.js`;
2. migration layers through `migrations-v16.js`;
3. provider, queue, recovery, crypto, and workspace cores;
4. `cross-device-transfer-core.js`;
5. `transfer-acceptance-core.js`;
6. `app.js` and earlier feature layers;
7. `features-v168-transfer-rehearsal.js`;
8. `features-v169-transfer-acceptance.js`;
9. `features-v169-meeting-day.js`.

The acceptance core depends only on `workspace-package-core.js`. The browser acceptance layer also depends on global download, announcement, and workspace functions created by earlier modules. Meeting-Day Mode runs last so dynamically inserted earlier panels can be classified as supporting panels.

## Storage boundaries

New storage values:

- `methodzTransferAcceptanceStateV169`
- `methodzTransferAcceptanceReportsV169`
- `methodzTransferRollbackReportsV169`
- `methodzPreRollbackBackupV169`
- `methodzMeetingDayPreferencesV169`
- `methodzWorkspaceDiagnosticsReportsV169`

The pre-import and pre-rollback packages contain workspace values and must be protected like complete business backups. Acceptance, rollback, and diagnostics reports are metadata-only.

## Mutation safety

Rollback is the only new workspace mutation path.

Before mutation it requires:

- a verified pre-import package;
- a fresh no-write replacement plan;
- explicit understanding confirmation;
- the typed phrase `ROLLBACK`;
- final browser confirmation;
- creation of a verified current-state package.

During mutation, v1.6.9 preserves transfer, acceptance, rollback, diagnostics, Meeting-Day preference, and recovery control keys. It verifies incoming values and required removals. On failure it restores the current-state snapshot and verifies that restoration.

## Service-worker boundary

The service worker caches only static files. It has no background sync, transfer, acceptance, rollback, queue, or workspace-data handler. All acceptance and rollback actions require an open page and direct operator action.

## Future consolidation candidates

Safe candidates for later review:

- shared HTML escaping and JSON download helpers;
- repeated recognized-key collection helpers;
- repeated bounded-report persistence;
- repeated workspace-limit normalization;
- repeated metadata-boundary objects.

Unsafe near-term consolidation candidates:

- save wrappers across governance and revision layers;
- record collection and migration order;
- external release and receipt routing;
- transfer apply and rollback transaction paths;
- archive and disposition overrides.

Those areas should not be rewritten until a dedicated regression-driven consolidation milestone exists.
