# Methodz Meeting Manager v1.6.5 Synchronization Rehearsal

## Purpose

Version 1.6.5 adds an explicit, browser-local synchronization rehearsal between the existing offline meeting workspace and the disposable v1.6.4 HTTP-style hosted-provider simulator.

It does **not** connect Firebase, Supabase, Google Drive, a CRM, or a Methodz production API. It stores no endpoint credentials and performs no automatic background synchronization.

The meeting-record schema remains `1.6.0`. Only the static application shell advances to `1.6.5`.

## Components

```text
config-v165.js
  Rehearsal storage keys, limits, tenant default, and fail-safe flags.

sync-rehearsal-core.js
  Portable queue, state machine, fingerprinting, retries, pull previews,
  conflict paths, explicit resolution, and metadata-only reports.

http-provider-pilot.js
  Existing serialized request/response simulator used as the disposable remote.

features-v165-sync-rehearsal.js
  Browser UI and localStorage-backed disposable remote workspace.

features-v165.css
  Responsive and print-hidden rehearsal presentation.
```

## Queue state machine

```text
offline
  Rehearsal connectivity is disabled. No provider request runs.

pending
  The user explicitly queued an operation and it is eligible to run.

retryable-error
  A rate limit, timeout, temporary outage, partial success, or dropped response occurred.

blocked-conflict
  Local content changed after enqueue, a remote conflict token changed,
  or a non-retryable provider condition requires review.

completed
  The requested operation or explicit conflict decision finished.
```

No timer, service worker, browser event, or background task processes queue entries automatically.

## Durable queue evidence

The queue is stored under `methodzSyncRehearsalQueueV165`. Each entry binds:

- tenant ID;
- operation (`push` or `pull`);
- record ID and a hashed record reference;
- source conflict token;
- stable idempotency key;
- canonical content fingerprint;
- source, base, local, and remote snapshots needed for browser-local conflict review;
- attempts, state, error code, timestamps, and explicit resolution metadata.

Queue snapshots are local workflow data. They are not authenticated remote audit records.

## Push rehearsal

1. The operator selects one or more saved local records.
2. `Enqueue Selected Push` creates queue entries without making a provider request.
3. `Process` or `Process Pending Queue` checks that the local fingerprint still matches the queued snapshot.
4. The disposable HTTP-style client sends an idempotent upsert.
5. A retry reuses the same idempotency key.
6. A stale conflict token or local mutation blocks the entry for review.

A dropped response after commit is reconciled by retrying the same request. The provider returns the original idempotent result instead of creating a duplicate write.

## Pull rehearsal

1. `Preview Remote Changes` lists disposable remote records and compares fingerprints.
2. Previewing does not alter local records.
3. Selected candidates are explicitly queued.
4. Processing verifies that the local baseline has not changed since enqueue.
5. Only then is the remote record written into the browser-local workspace.

## Conflict review

The coordinator reports changed field paths for base-to-local and base-to-remote comparisons. It never silently combines values.

Explicit actions are:

- **Accept Remote**: write the current disposable remote copy locally.
- **Keep Local**: complete the queue item without a remote write.
- **Rebase & Push**: bind the current local record to the latest remote conflict token, generate a new idempotency key, and return the item to `pending` for a separate explicit process action.

The field-path preview excludes field values from the rendered conflict summary and from exported reports.

## Tenant isolation

Each tenant receives:

- a distinct serialized provider namespace;
- distinct disposable remote active, archived, revision, and idempotency storage keys;
- tenant-scoped idempotency behavior;
- a hashed tenant reference in exported reports.

Changing the tenant does not merge or copy data between namespaces.

## Metadata-only reports

`Export Metadata-Only Report` includes:

- queue entry ID;
- hashed tenant and record references;
- operation and state;
- attempts;
- content fingerprint;
- hashed idempotency reference;
- presence, but not value, of a conflict token;
- error code and resolution strategy;
- timestamps;
- report integrity checksum.

It excludes meeting titles, notes, summaries, decisions, tasks, attendees, signatures, raw record IDs, raw idempotency keys, raw conflict tokens, credentials, access tokens, private keys, and private JWK parameters.

## Security boundary

The portable provider contract rejects:

- private JWK parameters;
- recognized private-key fields;
- embedded binary fields and data URLs;
- credential-shaped fields such as access tokens, API keys, passwords, and bearer tokens.

The rehearsal uses only localStorage and a same-page simulator. It does not prove authentication, authorization, tenant ownership, server durability, delivery, legal approval, or regulatory compliance.

## Deployment

The feature remains plain HTML, CSS, and JavaScript:

- no build command;
- no runtime package installation;
- no framework;
- no required server;
- direct-file core support remains available;
- static HTTPS hosting enables the optional service-worker cache.

The v1.6.5 app shell caches the rehearsal files so the interface can reopen offline. The service worker never executes queue operations and never stores meeting payloads itself.
