# Methodz Meeting Manager v1.6.10 Architecture

## Product boundary

Methodz Meeting Manager remains a task-focused meeting preparation, capture, analysis, archive, recovery, and records application. The panel registry organizes this application shell. It does not turn the repository into Method Hub, Nexus Hub, a storefront, the Cathedral, or shared production infrastructure.

The app shell advances to `1.6.10`. The meeting-record schema remains `1.6.0`.

## Why a registry

Earlier feature layers inserted cards dynamically and Meeting-Day Mode identified core sections by visible headings. That worked, but headings are presentation text and can change through localization, copy editing, or branding updates. Version 1.6.10 introduces a stable metadata contract for panels without rewriting the underlying meeting data model.

Each registered panel declares:

```text
id
label
group
selector
insertionAnchor
meetingDayPriority
meetingDayLabel
defaultVisibility
printBehavior
required
order
```

## Runtime layers

### `config-v1610.js`

Defines the app-shell version, valid registry groups, required capture IDs, visibility and print enums, bounded diagnostics, and the physical-device field-rehearsal boundary.

### `panel-registry-core.js`

A dependency-free browser and Node module. It owns:

- definition normalization and validation;
- duplicate-ID rejection;
- stable selector and insertion-anchor checks;
- required capture registration checks;
- required panel presence checks;
- Meeting-Day priority versus DOM-order validation;
- data-attribute binding;
- Meeting-Day panel resolution;
- metadata-only timing and shell diagnostics.

The core never reads meeting fields, records, signatures, credentials, private keys, or localStorage values.

### `panel-registry-definitions.js`

Registers the current shell incrementally:

- hero and quick actions;
- all nine direct meeting capture panels;
- saved records and Archive Vault;
- governance and provider panels;
- recovery, synchronization, Device Readiness, transfer, and acceptance panels;
- Meeting-Day controls and registry diagnostics.

Dynamic optional panels may be absent while their earlier feature module is disabled. Required capture panels may not be absent.

### `features-v1610-panel-registry.js`

Binds registry metadata after the earlier dynamic feature layers have initialized. It records a bounded metadata-only diagnostic and exposes a visible repair panel only when validation fails.

### Meeting-Day integration

`features-v169-meeting-day.js` now resolves registered panels by stable selector and priority. Heading matching remains only as a compatibility fallback for an older shell that does not load the registry.

If registry validation fails:

- the failure is visible;
- Meeting-Day navigation remains available for resolvable panels;
- supporting panels are not collapsed;
- meeting controls remain visible.

This is a fail-visible rather than fail-hidden design.

Changing a heading no longer changes Meeting-Day navigation.

## Order validation

Only panels with `meetingDayPriority` participate in strict workflow-order validation. This prevents optional dynamic infrastructure cards from producing false failures while still blocking a broken direct meeting sequence.

A priority/DOM mismatch emits `PANEL_ORDER_MISMATCH`, marks diagnostics invalid, and disables supporting-panel collapse until repaired.

## Diagnostics boundary

Registry reports contain:

- registered and resolved panel counts;
- missing, error, warning, capture, and Meeting-Day counts;
- expected and actual stable panel IDs;
- registration duration;
- aggregate browser script-load duration;
- error codes and static panel labels.

They exclude meeting content, raw record IDs, attendee names, signatures, credentials, private keys, and storage values.

## Service worker

The service worker caches the v1.6.10 static shell, including registry configuration, metadata, core, browser integration, and CSS. It has no background synchronization, transfer, acceptance, rollback, field-rehearsal, registry-data, or workspace-data handler.

## Field rehearsal artifact

`docs/V1.6.10-FIELD-REHEARSAL.md` defines the physical Android, iOS, tablet, and desktop release gate. `docs/field-rehearsal-evidence-template.json` provides a metadata-only evidence format.

The evidence artifact is operational documentation, not authenticated device proof.

## Compatibility

- Direct-file core meeting operation remains supported.
- Browser-local storage remains the default provider.
- Existing archive, governance, recovery, synchronization, transfer, and acceptance modules remain separate.
- The registry adds metadata and validation rather than moving business logic.
- No record migration, backend, credential, framework, or build command is introduced.
